# 共通開発方針：工程分割・容量管理・証拠保全

方針版：2026-11-14。対象は本人が管理する全リポジトリと、それらの作業環境・今後新設するリポジトリ。山中城専用の方針ではない。

## 1. 適用範囲と周知

- 共通方針の正本は本書とする。各リポジトリの AGENTS.md（既存の案内ファイルがある場合はその入口）から、正本のURLと採用した版またはcommitを参照する。既存の案件固有指示は保持し、競合する記載は対象・理由を記録して解消する。
- Hachibei-Labに文書を置くだけで他リポジトリの指示が自動更新されるわけではない。方針の対象範囲と、各リポジトリへの文書反映・既存スレッドへの周知の完了は区別する。
- 新規作業と進行中作業の次の大容量処理・マージ審査から適用する。過去のマージや保全記録を遡って成功・失敗に書き換えない。既存成果の再生成・再複製は一律に要求せず、利用可能な原証拠と照合記録を参照する。

## 2. 工程分割と大容量データ

1. 原則として1工程・1つのPRは1つの明確な目的とし、区域・施設・部品・検証目的の単位で限定する。コードの行数や変更ファイル数を一律の分割基準にしない。
2. Blender、QGIS、CAD、地形メッシュ、画像、動画、ブラウザーのtrace、アーカイブ等の入力・中間生成・出力データの容量、再生成負荷、実行時間を重視する。
3. 既存の原本を毎回複製せず、参照・差分・変更範囲だけの再生成を優先する。原本を変更せずに派生物を別の出力先へ生成する。
4. 編集原本とWeb配信用データを区別する。容量抑制のために史料根拠、編集原本、出所、hash、再生成に必要な手順・条件・依存関係を失わない。
5. 一時生成物、バックアップ、キャッシュ、テストのスクリーンショット・動画・trace、圧縮時の一時コピーも容量計測と予算に含める。
6. 大容量の原証拠や再生成可能な派生物を毎回Git履歴へ追加せず、必要なコード、検証台帳、メタデータ、再生成手順と保全先への参照を管理する。公開可否が未確認の資料や本人限定の保存先・識別情報を公開しない。

## 3. 処理前後の容量確認

- 処理開始前に、対象範囲、入力データ量、推定生成量、処理途中の最大追加使用量、必要な余裕、容量予算、実効書込先とその空き容量を記録する。完成物のサイズだけで開始可否を判断しない。作業領域とTempが同じ容量を共有する場合は二重計上して余裕があるように見せない。
- bytes、inode、mount等は環境に応じて確認する。適用不可は NOT_APPLICABLE、取得失敗・測定不能は UNKNOWN と区別する。適用可能な重要指標が不明、容量予算超過が見込まれる、または必要な余裕がない場合は大型処理を開始せず、先に工程を縮小・分割する。実行中に超過や不足を観測した場合は、安全に停止できる範囲で自分の処理を停止し、既存成果を保持して次工程を分割する。
- 処理後は入力・中間・出力・Tempの実測容量、開始前からの増加量、生成ファイル数、観測できた最大使用量、保全先と検証状態を記録する。最大使用量を観測していない場合は推定値と実測値を混同しない。
- 案件専用の一時領域と子プロセス限定の設定を優先する。パスの分離を、物理容量やquotaの独立と取り違えない。未検証の共通ツールやLinux専用の結果を別環境へ無条件に転用しない。
- 元データ、既存成果、共有Temp、他案件ファイルを削除・移動・上書きしない。再生成可能そうなキャッシュを理由とした自動清掃も行わない。

## 4. マージ時の証拠保全条件：本人限定Spaceでの照合を認める

**保全が必要な対象を本人限定のChatGPT Spaceへ保存し、保存後にSpaceから実ファイルの全バイトを再取得して元データと照合できれば、当該対象のマージ審査における保全条件を満たす。Windowsへの追加移管、外付け二重保全、永久保存の証明を、そのマージの必須前提にはしない。**

- 認可済みWindows等へ保存し、保存後の実ファイルを独立読戻しして同じ照合条件を満たす経路も有効とする。Spaceへの直接保存を認め、Windowsへの保存失敗を先に試すことは要求しない。
- 対象HEAD、必要に応じたtree、証拠の出所・生成条件、対象ファイルの件数・サイズ・SHA-256、保存先と本人限定のアクセス範囲を台帳で対応付ける。保存先の非公開識別情報は本人限定台帳で保持し、公開PRには必要最小限の状態を記す。
- 保存後の照合は、アップロードに使ったメモリーやローカルコピーの再ハッシュではなく、保存先から実際に再取得したバイト列を別工程または別プロセスで読み、元データおよび台帳とサイズ・全バイトSHA-256が一致することを確認する。保存応答、ファイル名、メタデータ、アップロード時のhashだけで保全PASSにしない。
- 複数ファイルをZIP等にまとめた場合は必要な対象が揃っていることを台帳と照合し、存在し適用できるCRC・内部manifestも確認する。ZIPのhash一致だけで梱包前の必要証拠の欠落まで解消したと扱わない。再取得不能・欠落・不一致は範囲と原因に応じ PENDING / PARTIAL / UNKNOWN / FAIL / BLOCKED とする。
- このPASSは確認した対象・保存時点の保全結果であり、Spaceの無期限保持やあらゆる障害からの復元を証明しない。長期保持が未確認ならUNKNOWNを記録し、Windowsへの追加移管や二重保全は別の継続課題とする。
- 保全PASSは元データの削除・移動・上書きの許可ではない。過去の失敗票や旧原本を保持する。

## 5. 技術的受入とマージの実行

- 証拠保全条件と技術的受入条件を分けて判定する。Spaceで保全PASSなら保全先だけを理由にマージ不可としない。一方、対象範囲に必要な試験、正式CI、独立レビュー、史料・地形・3Dの整合性、安全性、重要な未解決事項の評価は維持する。
- 容量抑制を理由に必要な検証を省略しない。静的確認・単体・少数条件から段階的に進め、対象に必要な検証範囲を満たす。
- この方針だけで自動マージや公開を許可しない。マージ実行の明示指示と既存の案件固有条件は引き続き確認する。独立成果の限定採用可否は、その対象範囲に対して判断する。
- 専用Issue・branch・commit・push・Draft PRで履歴を残す。GitHub等で提出する文書と、非公開の原証拠を分ける。

## 6. 各工程・PRでの記録項目

| 項目 | 記録する内容 |
|---|---|
| 対象 | 目的、対象区域・施設・部品・検証、変更範囲、HEAD |
| 処理前 | 入力量、推定生成量、推定最大追加使用量、予算、必要な余裕、実効書込先と空き容量 |
| 処理後 | 入力・中間・出力・Temp容量、増加量、生成ファイル数、観測した最大使用量 |
| 保全 | 対象の網羅、保存先、アクセス範囲、保存後の実バイト再取得／独立読戻し、サイズ・SHA-256照合結果 |
| 技術的受入 | 必要な試験・CI・独立レビュー、未解決事項、史料・位置・3D等の整合性 |
| 判定 | 保全条件と技術的受入を分けた状態、限定マージ可否、残件 |

未測定・未実施・適用不可は UNKNOWN / NOT_TESTED / NOT_APPLICABLE と理由を示す。文書だけの小規模変更にCADやブラウザーの再生成を要求するなど、対象に無関係な処理を増やさない。

## 7. 各リポジトリへの導入

1. 既存のAGENTS.md・README・PRテンプレートと進行中PRを確認する。
2. 既存の指示を保持し、本書への参照と「本人限定Spaceで保存後の実バイト再取得・サイズ・SHA-256一致を確認すればマージ時の保全条件を満たす。Windows追加移管は必須としない」を入口へ明記する。
3. 全リポジトリが対象であることと、そのリポジトリへの反映PR・採用版・周知状態を記録する。未反映・未確認を反映済みと報告しない。進行中のスレッドは新規指示ファイルを自動で読むと仮定せず、次の依頼で参照先・版を伝える。
4. 既存の過去記録は消さず、新方針による今後の判定を追記する。未解決の技術課題を保全方針の変更だけで解消済みにしない。
